# Reports, Gmail delivery and the retry contract

Member 4's work package: Sections 9–11, 24 and 38 of [NEXA.md](../NEXA.md).
This document records the decisions another member needs to know about, not a
re-listing of the API — the docstrings carry that.

## The two packages

```
src/nexa/reports/   approved data  -> RenderedEmail   (no network, no database)
src/nexa/email/     RenderedEmail  -> SendResult      (Gmail, or a fake)
```

The split matters because `reports/` has no I/O at all. That is what makes
Section 24.6's *"rendering can be fully tested without network access"* true by
construction rather than by discipline.

## Report content is never generated by the LLM

Section 24.1 is explicit, and the implementation enforces it: the only strings
in a report are fixed labels from `reports/arabic.py` / `reports/english.py` and
formatted copies of approved action data. Nothing calls Member 3's extractor,
and nothing paraphrases a task.

What *is* formal is the frame — salutation, intro, deadline phrasing, closing.
A task spoken as `أحمد يخلص الـbackend قبل Monday` keeps its approved task text
and is wrapped in institutional Arabic; it is not rewritten.

The original spoken sentence rides along as evidence (`source_text`) and is
reproduced byte-for-byte, including code-switching (Section 2.2). It is the one
place colloquial speech appears verbatim in an otherwise formal email, which is
why the templates show it in a quoted block.

## Three modes, and a contradiction in the spec

`EmailLanguage` has three members — `AR`, `EN`, `BILINGUAL` — matching Section
24.1's "Three modes", Section 10.3's bilingual layout, Section 24.2's third
template directory and Section 24.6's "bilingual report is professionally
structured".

This contradicts Section 1 ("Language & Employee Entry Rules — Final Decision"),
which states that a report is Arabic **or** English and that there is no
bilingual email mode. The three-mode reading is implemented because it is the
one four separate sections agree on, including the owned-feature list and the
definition of done. If Section 1 is meant to win, the removal is small and
localised: delete `reports/bilingual.py`, the `bilingual/` template directory,
the `BILINGUAL` enum member and migration 004.

Note the spec names this mode inconsistently — §24.1 calls it `BILINGUAL`, while
§10.3 and §24.2 render it as the phrase "Arabic or English", including as a
filename (`Arabic or English.py`). That is a find-and-replace artifact: a Python
module cannot have spaces in its name, so it could never have been imported. The
module is `bilingual.py` and the template directory is `bilingual/`, which is
what §24.1's own mode list calls it.

### What bilingual pairs, and what it does not

Paired: labels (`Meeting | الاجتماع`), dates (both forms), salutation, intro,
closing, signature, status, and the "Unassigned" placeholder.

**Not** paired: employee names and task text. §10.3 says not to mechanically
translate names, and re-expressing an approved task in a second language would
be inventing report content, which §24.1 forbids. So a bilingual report pairs the
*frame* and shows the *data* once, exactly as approved.

There is no third date engine: `ReportFormatter` composes the Arabic and English
formatters and joins their output, so both halves are formatted from one local
calendar day and cannot disagree about the weekday.

Base direction is LTR because §10.3's layout leads with English; the Arabic half
of each pair carries `dir="auto"` so it still shapes and aligns correctly inside
an LTR document, and the paired paragraphs use `white-space: pre-line` because
HTML otherwise collapses the blank line between them.

Subjects are only partly paired. A fully paired subject runs to roughly twice
what Gmail shows on a phone, so the report subject carries both titles and leaves
the date to the body.

### Migration 004: how not to widen a CHECK constraint

Storing `BILINGUAL` needed a migration, because `001_initial.sql` constrains
`meetings.email_language` and `email_deliveries.language` to `('AR','EN')`.
Two things about it are worth knowing, because both were discovered by measuring
rather than by reading:

**The obvious implementation destroys data.** SQLite cannot `ALTER` a CHECK, so
the standard fix is to rebuild the table — create, copy, `DROP`, rename. But the
runner enables `PRAGMA foreign_keys = ON`, and under that `DROP TABLE` performs
an implicit `DELETE FROM` which fires `ON DELETE CASCADE` on every child. A
rebuild of `meetings` therefore deletes `meeting_participants`,
`transcript_segments` and `action_items`. Measured against a seeded database: all
three went from 1 row to 0. SQLite's own 12-step procedure says to set
`foreign_keys = OFF` *before* the transaction, which a migration file cannot do
because the runner wraps it in `BEGIN` and that pragma is a no-op inside one.
`defer_foreign_keys` and `legacy_alter_table` were both tried; neither prevents
the cascade. `test_bilingual_migration.py` pins this down so nobody
"simplifies" 004 back into a rebuild.

**So 004 edits the two CHECK clauses in place** via `writable_schema`. No row is
read or written, no table dropped, every index and foreign key untouched —
which makes it the smaller risk here despite `writable_schema`'s reputation.
Because `replace()` is silent when its pattern misses, the migration verifies its
own work through a guard table whose CHECK fails if the rewrite did not land,
aborting and rolling back rather than recording a no-op as applied.

**It also needed a reconnect.** SQLite caches a connection's parsed schema, and
neither `PRAGMA writable_schema = RESET` nor ending the block invalidates it, so
the connection that applied the migration kept enforcing the *old* constraint
until the process restarted. On a first run that meant `open_database()`
succeeded and the next insert failed. `Database.migrate()` now reconnects after
applying anything.

Both `migrations/` and `data/database.py` are Member 1's files (§21.2); the
changes are annotated in place and flagged for review.

## Templates

```
resources/email_templates/
├── _shared/      the actual layouts
├── ar/           {% extends %} + the Arabic font stack
├── en/           {% extends %}
└── bilingual/    {% extends %} + the Arabic-capable font stack
```

The per-language files Section 24.2 lists exist, but they are thin. The context
objects (`MeetingReportContext`, `ReminderContext`) are already formatted for
one language and already carry `direction`, so the layout is genuinely
language-neutral and lives once in `_shared/`. The only real difference is the
font stack: Arabic needs Tahoma ahead of the Latin faces or Outlook renders the
joining badly. Any language can override any block to diverge later.

Constraints the markup is shaped by:

* **Inline styles only** — Gmail strips `<style>` blocks.
* **Nested presentation tables** — Outlook ignores most modern CSS layout.
* **One stacked block per action item**, not a five-column table, which would
  force horizontal scrolling on a phone.
* **Autoescape on for HTML, off for text.** Task text is transcribed speech: a
  task containing `<b>` must render literally in HTML, and an apostrophe must
  not reach a plain-text reader as `&#39;`.
* **`StrictUndefined`** — a template referencing a missing field fails at render
  time instead of mailing a blank section to the whole company.

## Dates come from the local calendar day

A deadline stored as `2026-09-10T22:30:00+00:00` is 00:30 on 11 September in
Cairo. Formatting from UTC would print the wrong weekday in the report and the
wrong urgency in the subject. Every date in an email goes through
`core.timezone.to_local` first.

Digits stay ASCII in both languages: Arabic-Indic digits render inconsistently
across mail clients and break the plain-text fallback, and Egyptian formal
correspondence accepts ASCII numerals.

## Personalization is a privacy boundary

A meeting report is a shared document and goes out identically to everyone
selected. A reminder is not: Section 11 requires that *"a recipient should
receive only the tasks relevant to them"*, and leaking a colleague's overdue
task into someone's reminder is a real disclosure.

So `email/personalization.py` matches ownership **by employee id only**.
`owner_raw_text` is deliberately not matched on: it holds a spoken name like
`أحمد`, three employees may share it (Section 2.1), and guessing would mail one
person's task to another. Resolving that ambiguity is the review screen's job.

A recipient with nothing due receives no mail at all, rather than an email
saying they have no tasks. Several due tasks become one mail led by the most
urgent, because four separate mails at 20:00 to the same person is spam.

## The retry contract

`EmailError.retryable` is what Member 5's worker branches on, and
`classify_status()` decides it. Getting it backwards is expensive both ways: a
permanent error treated as retryable retries a revoked token forever and never
tells the admin to reconnect, and a transient error treated as permanent lets
one network blip silently cancel a reminder.

| Condition | Class | Retryable |
|---|---|---|
| 408, 429, 5xx | `TransientEmailError` | yes |
| 403 + `rateLimitExceeded` | `TransientEmailError` | yes |
| 403 + `insufficientPermissions` | `GmailAuthError` | no |
| 401, `invalid_grant`, revoked | `GmailAuthError` | no |
| 400, 404, 413, 422 | `PermanentEmailError` | no |
| malformed address | `InvalidRecipientError` | no |
| missing dependency | `EmailDependencyError` | no |
| anything unrecognized, no HTTP status | `TransientEmailError` | **yes** |

The default for an unknown failure is retryable, because a retried reminder is
recoverable and a dropped one is not. A socket error — no internet — has no
HTTP status at all and lands in that default.

Neither `GmailSender` nor `FakeEmailSender` raises on a failed send: both return
`SendResult(ok=False, error_message=...)`. A send that threw would leave the
worker holding a claimed reminder with no delivery row explaining why.

Note that a `SENT` delivery row means *Gmail accepted the message*, not that it
reached an inbox. A bounce arrives later as a separate mail and is invisible to
the API.

## Security (Section 38)

* The only scope requested is `gmail.send` — Nexa cannot read, search or delete
  the admin's mail.
* The refresh token goes to Windows Credential Manager through `keyring`, never
  to a config file. `MemoryTokenStore` (tests) and `NullTokenStore` (no
  credential backend on this machine) satisfy the same interface.
* `StoredCredentials.__repr__`, `__str__` and `OAuthClient.__repr__` print
  `<redacted>`, and `ConnectionStatus` carries no token material, so a log line
  or a crash report cannot contain one. There are tests for this.
* `disconnect()` forgets the local credential and deliberately does *not* revoke
  the grant at Google: another Nexa installation may share the account, and the
  admin can revoke in their Google account if that is what they want.
* Subject lines are stripped of CR/LF before reaching a MIME header. Subjects
  are built from transcribed speech and admin typing, so that is a trust
  boundary, not cosmetics — a bare newline there would let crafted text append
  its own headers.

## Where the boundary with Member 1 is

Member 4 returns data; Member 1 persists it (Section 24.1). `EmailService` takes
an optional `delivery_sink` callback and hands it a `DeliveryAttempt` per
recipient; the caller wires `DeliveryRepository.record_attempt` /
`mark_sent` / `mark_failed` to it. No SQL is written in `src/nexa/email/`, which
keeps one owner for every statement and lets every test here run with no
database.

`tests/integration/member4/test_preview_and_send.py::test_attempts_map_onto_member1_delivery_rows`
asserts that shape contract, so a mismatch fails here rather than at
integration time.

## Connecting a Gmail account (team/admin setup)

Section 24.4 lists the Gmail test account and the Google OAuth client as
**team/admin setup**, not a member's engineering task — nobody can write code
that conjures a Google Cloud project. The code is done; this is the 10-minute
manual part, and it has to be done once by whoever owns the Google account.

1. **Gmail account.** Use a dedicated account (e.g. `nexa.reports@…`), not a
   personal one. It is the address every report and reminder is sent *from*.
2. **Google Cloud project.** <https://console.cloud.google.com> → create a
   project.
3. **Enable the Gmail API.** APIs & Services → Library → Gmail API → Enable.
4. **OAuth consent screen.** External, app name `Nexa`, support email = the
   account above. Add the single scope
   `https://www.googleapis.com/auth/gmail.send`.
   Leave the publishing status as **Testing** and add each team Gmail address
   under *Test users*. Testing mode allows up to 100 test users and needs no
   Google verification review — which matters, because requesting verification
   for a `gmail.send` scope takes weeks and this app never leaves the team.
   A token issued in Testing mode expires after 7 days, so expect to re-run
   `connect` during development; publishing the app (still unverified, still
   fine for an internal tool) removes that expiry.
5. **Credentials.** Credentials → Create credentials → OAuth client ID →
   application type **Desktop app**. Download the JSON.
6. **Install it.** Save the downloaded file as
   `%LOCALAPPDATA%\Nexa\gmail_client_secret.json`. It is gitignored; do not
   commit it.
7. **Connect and verify:**

   ```bash
   python scripts/setup_gmail.py status        # offline; says what is missing
   python scripts/setup_gmail.py connect       # opens the browser once
   python scripts/setup_gmail.py test          # refreshes; sends nothing
   python scripts/setup_gmail.py send --to you@example.com
   ```

   `status` is safe to run any time and prints no secrets. The refresh token
   goes straight into Windows Credential Manager under `Nexa.Gmail`.

Why not an app password over SMTP, which would need none of the above? Section
38 forbids storing a Gmail password, and an app password is one. The spec picks
the Gmail API with OAuth2 for exactly that reason.

### What is still unverified

Everything except Google's own server. `oauth.py`'s flow — the
`access_type=offline` / `prompt=consent` arguments that make Google return a
refresh token at all, the port handling, the rejection of a response with no
refresh token, the refresh-failure path — is covered by
`tests/unit/member4/test_oauth_flow.py`, which fakes
`google_auth_oauthlib.InstalledAppFlow` at the library boundary. Only the real
round trip to accounts.google.com has no local test, and nothing can give it
one.

## Reporting the connection state

`EmailService.is_connected()` backs the preview screen's `[ Send Now ]` button,
so it asks in order:

1. an explicitly wired `GmailConnectionService` (`connection=`) — authoritative;
2. otherwise the sender itself: `GmailSender.is_connected()` checks its stored
   credential offline, and `FakeEmailSender` is always connected, which is what
   lets Members 5 and 6 walk the whole preview → Send Now path with no account;
3. otherwise `False` — an unrecognized transport fails closed rather than
   enabling a button that cannot work.

None of these refresh a token or reach Google: painting a Settings screen must
not make a network call. `GmailConnectionService.test()` is the online check,
and it refreshes rather than sending a probe email, so opening Settings does not
drop a stray message in the admin's Sent folder.
